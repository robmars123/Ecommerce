### 13.2 Architecture decisions

| Decision | Chose | Gave up | Why |
|---|---|---|---|
| Monolith vs microservices | Modular monolith | Independent deploys | Checkout + reservation + order in one transaction. Distributed transactions make the core invariant harder |
| Inventory lock | Postgres `FOR UPDATE` + check constraint | Some raw throughput | Truth stays in Postgres; Redis loss can't oversell |
| Reserve vs decrement at checkout | 15-min reservation, commit on Paid | Stock held briefly by abandoned checkouts | Keeps "paid but no stock" and "stock lost to abandoned carts" separate problems |
| Payment truth | Signed webhook | Slower UI confirmation | The client can be faked, refreshed, or closed |
| Search | Postgres full-text | Advanced ranking and facets | Not the bottleneck at launch |
| Read models | Outbox + in-process projectors | Broker features (fan-out, retention tooling) | Same transaction guarantees; no new infrastructure in v1 |
| Fulfillment | Manual admin transitions | Automation | State machine + audit are the lesson; automation plugs into the same transitions |
| Readiness vs Redis | Postgres + migrations gate Ready; Redis only degrades | Early warning that cache is down via readiness | A Redis outage must not pull traffic when cache-aside still serves correct data |
| Backend project layout (owner decision, Nathaniel, 2026-11-03) | **Module + Contracts**: per module `Ecommerce.<M>` (internal implementation with Domain/Application/Infrastructure/Api folders) + `Ecommerce.<M>.Contracts`; shared `Ecommerce.SharedKernel`, `Ecommerce.Persistence`; host `Ecommerce.Api`. Replaces the shared layer projects (`Ecommerce.Domain/Application/Infrastructure`) organized by module folder | Fewer projects; layer purity enforced by assembly references (Domain could not reference EF at all) — now layers are folders checked by architecture tests (signatures + source scan) | Module boundaries become compiler-enforced: a module cannot reference another module's implementation, and `internal` types make cross-module entity or service use impossible to compile. Still one deployable modular monolith; stack lock unchanged. **Revisit when** project count slows the build measurably, or a module needs its own process (§10.4) |
| DbContext layout (re-argued for Module + Contracts) | One `EcommerceDbContext` in `Ecommerce.Persistence`, one migration stream and history table, `public` schema; modules plug in internal `IModuleDbModel` configurations | Per-module DbContexts, schemas, and migration histories (fully independent persistence per module) | §8.2 needs inventory + order + payment + outbox in **one** transaction; one scoped context makes that the default instead of a cross-context shared-connection protocol. Moving tables to per-module schemas breaks rule 18 (the previous image reads `public.*`). Rule 8 is compiler-enforced by internal entity types. **Revisit when** a module is extracted (§3.1.4) |
| Migrations location | Migrations + snapshot in `Ecommerce.Persistence`; `IDesignTimeDbContextFactory` in the host (`Ecommerce.Api/Composition`) built from the same `AddEcommerceModules` composition as runtime; `Microsoft.EntityFrameworkCore.Design` referenced by the host with `PrivateAssets=all` (existing package, version already pinned — not new) | `Design` assemblies ship in the API image; a separate `Ecommerce.Migrations` project would avoid that | The design-time model must include every module, and only the host references every module. One composition function for runtime and design time means the drift check cannot miss a module. Migrations stay in the context's own assembly, so no `MigrationsAssembly` setting can silently find zero migrations |
| Module controllers | `internal` controllers in `Ecommerce.<M>.Api`, discovered by a host `ModuleControllerFeatureProvider` over the module assemblies | MVC's default public-only discovery | Public controllers would force their services, criteria, and result types public, leaking the module's implementation |
| Clock in the host | `SystemClock` lives in `Ecommerce.Api/Time` and is registered by the host; everything in `SharedKernel`, `Persistence`, and `Modules/` reads time only through `IClock` | — | Rule 9, widened: the architecture test scans all of them, so the only system-clock read is in the composition root |
| Frontend styling (owner decision, Nathaniel, 2026-11-03) | **Tailwind CSS via NativeWind** — `className` + tokens is the default (§5.4, §5.5). NativeWind 4.2.x + `tailwindcss` 3.4.x (v3 LTS), `react-native-reanimated` as NativeWind's peer at the Expo SDK version; exact pins at adoption. Replaces plain `StyleSheet.create` as the default (it stays for runtime, animated, and no-`className` props). Adoption is a separate step only when Nathaniel asks | Zero-config styling; cost: `babel.config.js` (`jsxImportSource` + `nativewind/babel`), `metro.config.js` (`withNativeWind`), a `global.css` entry imported in the root layout for web, the NativeWind transform running under `jest-expo`, `nativewind-env.d.ts`, and one more package to move with each SDK upgrade | Owner's choice: one styling vocabulary on all three platforms and tokens in one place. Version choice (Rob): NativeWind 4 is the npm `latest` (4.2.7) and its `react-native-css-interop` 0.2.7 peers require `tailwindcss ~3` and `react-native-reanimated >=3.6.2` (SDK 58 bundles 4.7.1, already in the tree via `expo-router`). NativeWind 5 (Tailwind v4) is only `5.0.0-rc.1` — no pre-release in the stack. npm metadata declares no Expo SDK range, so SDK 58 / RN 0.88 support is proven at adoption by the §4 gates plus an Expo Go check, not assumed. **Revisit when** NativeWind 5 is stable |
| Frontend exports and imports | Named exports + `@/` alias everywhere except `app/` routes (default, router-mandated) | Shorter `import X from` lines; relative paths with zero config | Named exports keep one name across files (grep, rename, auto-import); the alias survives moving files between features. Both use built-in Expo/TypeScript support — no new package |
| Frontend test runner | Jest via `jest-expo` + RNTL + `expo-router/testing-library`, dev dependencies only (§2 amendment, owner-approved) | Zero-dependency frontend; Vitest speed | The frontend had no runner, so F4–F6 (client side of rules 1, 2, 5) could not be proven. Replaces nothing; never shipped in the bundle |
| Test enforcement | CI fails on zero discovered tests (backend `TreatNoTestsAsError`, Jest default) and on focused tests; coverage uploaded as an artifact with **no % gate** | A coverage number to point at | Quality bar §5: coverage proves nothing about oversell. A silently empty or focused suite is the real hole |
| Route test location | Top-level `tests/` (`tests/routes.test.tsx`, `tests/app/<route path>.test.tsx`) | Strict co-location for routes | Expo Router turns every file in `app/` into a route, so route tests can't sit beside their file |
| Lint / format in CI | Not gated (no ESLint, no `dotnet format --verify-no-changes`) | Automatic style consistency | Quality bar §3: style never blocks. `tsc --strict` and `dotnet build` are the static gates. Revisit at Slice 7 with the warnings-as-errors switch |
| Local Postgres 17 | Docker only (Testcontainers + Compose on 127.0.0.1:5434, trust auth) | Native-DB speed | Stack lock is PG17; CI and local use the same engine; no secret in local config |
| Stock indicator before Inventory exists (1a) | Catalog calls `IInventoryReader` (Inventory's contract) once per request; Slice 1a registers a stub returning `Unknown`, and the UI shows no badge for `Unknown`. Slice 2 swaps the registration; Slice 7 caches it 10s | A visible indicator in 1a | Rule 8 — no cross-module DbSet/join; never claim "In stock" without data; Inventory classifies (threshold), Catalog never sees quantities |
| Search source in 1a | Generated weighted `tsvector` + GIN on the `products` table (system of record) | Read-model decoupling until 6b | Strongly consistent and correct now; the 6b search projector replaces the source behind `ICatalogReadStore` with the same HTTP contract |
| Money on the wire | Decimal **string** + currency (`{ amount: "24.50", currency }`) | Arithmetic-friendly JSON numbers | Rule 1 — JS parses JSON numbers as binary floats; the client only formats |
| Dev data and images | Development-only, config-gated, idempotent seeder via domain + EF (startup fails if enabled outside Development); image URL = config `Catalog:Images:BaseUrl` + key, `null` while the placeholder is empty | Realistic images in local dev | "No direct SQL" and §2 open decisions — no invented bucket/CDN domain |
| CORS | `Cors:AllowedOrigins` config only (`http://localhost:8081` in Development; empty in committed prod config), no credentials in 1a | Zero-config cross-origin | §10.1 — configured origins only; production origin is an open decision |
| Expo SDK patch alignment (Rob, 1a review) | CI keeps `npx expo install --check` as a blocking gate; when Expo publishes new SDK patches, the next slice aligns them with `npx expo install --fix` and re-pins exact. That is not a new package (same package, SDK-recommended patch) | A hermetic CI: the check reads Expo's live recommended versions, so it can turn red with no code change | Native-module/SDK mismatch is invisible in Jest and web export but breaks EAS builds and Expo Go; a red gate is the cheap warning. Any slice whose diff fails it is blocked |
| Catalog list query shape (1a) | One EF statement: page subquery (`LIMIT/OFFSET`, unique tie-breaker) joined to `ROW_NUMBER() OVER (PARTITION BY product_id)` derived tables for cheapest active variant and first image; count is a separate statement (2 round-trips) | Per-page-only work: the window may scan all active variants/images before the join | Correct and N+1-free at launch scale. **Slice 7 slow-query item:** measure; if needed, a `LATERAL ... LIMIT 1` or a denormalized "from price" column. Count and page are separate snapshots (READ COMMITTED), so a publish between them can skew `totalCount` by one — acceptable for display |
| Identity store (Slice 1b) | **Chose:** a module-owned `users` table and an internal domain `User`. Hashing is ASP.NET Core Identity's `PasswordHasher` (shared framework, no package). Lockout, roles, and reset tokens are module domain logic on `IClock`. No `UserManager`, no Identity EF stores | **Gave up:** Identity's ready-made 2FA, external logins, and confirmation tokens | Framework `IdentityUser` entities would break module-internal model ownership (§6.2) in the single context. Lockout must run on `IClock` and inside our row lock. Identity reset tokens need a shared Data Protection key ring. The tested crypto stays Microsoft's. **Revisit when** SSO, social login, or 2FA is in scope |
| Refresh tokens (Slice 1b) | **Chose:** opaque 256-bit tokens, SHA-256 hashed, in families. Every refresh rotates; reuse of a consumed token revokes the family; **no reuse grace window**. Sliding 14 days, absolute 30 days. Family row locked per refresh | **Gave up:** tolerance of a lost refresh response (the client retries and the user is logged out); instant access-token revocation (≤ 15 min window) | Theft becomes detectable. A DB leak yields no usable tokens. Client single-flight prevents self-inflicted reuse. **Revisit when** forced logouts from flaky networks are measured: a short reuse interval that returns the same child |
| Web token transport (Slice 1b) | **Chose:** web refresh token only in an httpOnly `SameSite=Strict` cookie, honoured only with the `X-Auth-Transport: cookie` header (forces a CORS preflight, which acts as the CSRF guard). Native uses the body plus SecureStore. Access token in memory on both | **Gave up:** one transport for all clients | XSS can't exfiltrate the long-lived credential (§5.2). **Constraint on the open domain decision:** web origin and API must be the same site. **Revisit when** they can't be: a backend-for-frontend, or `SameSite=None` plus CSRF tokens |
| Registration enumeration (Slice 1b) | **Chose:** register returns 409 for an existing email. Login and reset don't reveal accounts | **Gave up:** enumeration-proof registration | It needs verify-first registration, which needs an email provider (open decision) and email verification (not v1 scope). Mitigated by Slice 7 rate limits. **Revisit when** a provider exists and abuse is measured |
| Password-reset delivery (Slice 1b → 6) | **Chose:** the token hash commits first; then, outside any transaction, an `IPasswordResetLinkSender` runs. In Development it writes to a pickup directory (`artifacts/dev-mail`); elsewhere it logs a no-provider Warning with no token. No token in any log | **Gave up:** guaranteed delivery in 1b | No provider exists (§2), so 1b makes no external call (rule 6). **Slice 6:** outbox event `PasswordResetRequested`, with the consumer minting the token, so plaintext is never stored |
| Concurrency style (Slice 1b) | **Chose:** pessimistic row locks for auth, with a global order `users → refresh_token_families → refresh_tokens` and `users → password_reset_tokens`. Optimistic `xmin` version for admin product edits (stale → 409) | **Gave up:** a lock-free auth path; merge-style editing | Auth critical sections are server-side milliseconds, and locking before verifying the password stops parallel guesses beating lockout. Human edits have think time, so a lost update is detected, not prevented by a lock |
| Authorization default (Slice 1b) | **Chose:** fallback policy "authenticated user"; public endpoints opt out with `[AllowAnonymous]`; a test pins the anonymous endpoint list. Unmatched routes reach one anonymous terminal endpoint (`MapFallback`, 404), because the fallback policy otherwise answers 401 for a route that doesn't exist | **Gave up:** a little ceremony on public endpoints; 405 for a wrong method on a real route (it is 404) | A forgotten attribute fails closed (401), never as a public admin endpoint. The 404 endpoint runs no handler and is on the pinned anonymous list |
| Write-DTO validation (Slice 1b) | **Chose:** FluentValidation (core package) in module `Api` folders, called explicitly by controllers; strict JSON (`UnmappedMemberHandling.Disallow`) | **Gave up:** lenient forward-compatible request parsing | §10.1 names FluentValidation. Strict binding makes mass assignment a 400. `FluentValidation.AspNetCore` auto-validation is deprecated and is not used |
| JWT signing (Slice 1b) | **Chose:** HS256 with the algorithm pinned, a ≥ 32-byte key from user-secrets or env. Development generates an ephemeral key when none is set; any other environment fails to start without a key | **Gave up:** asymmetric keys and JWKS | One process issues and validates, and no secret is committed. Rotating the key costs one silent refresh, because refresh tokens are DB-backed. **Revisit when** another service validates tokens (RS256/ES256 + JWKS) |
| Admin bootstrap (Slice 1b) | **Chose:** `Identity:Bootstrap:AdminEmail` and `AdminPassword` from secret config. On startup, create the Admin if missing; **never promote** an existing account | **Gave up:** "promote my existing account" convenience | Registration is open and unverified, so promote-by-email could be squatted. Create-only fails visibly instead |


| Stock indicator `Low` threshold (features 1–6 docs, Rob) | **Chose:** one config value `Inventory:LowStockThreshold`, default 5, per variant on available = on_hand − reserved; no stock row = `Out`; `Unknown` kept in the enum but no longer emitted from Slice 2 (§7.4) | **Gave up:** per-variant or per-category thresholds | One number covers the display-only indicator; per-variant thresholds need an admin field no v1 feature asks for. The enum isn't narrowed because v1 is never silently changed (§9) |
| Guest device-cart storage (planned Slice 3 package) | **Chose:** Zustand `persist` with `@react-native-async-storage/async-storage`, installed via `npx expo install` (SDK-pinned) in Slice 3. Its web build uses `localStorage`, so one package covers web, Android and iOS with no `lib/platform` split. Stores only variant, slug, quantity and a display snapshot | **Gave up:** reusing the installed `expo-secure-store` (Keychain/Keystore for non-secret data, ~2 KB value guidance would force an unplanned guest line cap, no web support); MMKV (needs a dev build, not Expo Go); raw `localStorage` + a native split (two code paths) | Smallest option that runs in Expo Go and the web export; Zustand is already in the stack lock for cart UI state. Nothing in it is secret or authoritative — merge re-validates everything |
| Cart edit quantity and merge idempotency (Slice 3) | **Chose:** `PUT /cart/items/{variantId}` sets the quantity (1 … `Cart:MaxQuantityPerLine` default 10, ≤ available, 0 removes, absent line 404); `POST /cart/merge` requires an `Idempotency-Key` (scope `cart-merge`) | **Gave up:** `PATCH` with deltas; a non-idempotent merge | Set-semantics make a retried `PUT` harmless; deltas double on retry. A merge whose response is lost would otherwise double quantities when the client retries (§8.1) |
| Checkout address (v1 minimum) | **Chose:** an inline address in the `POST /checkout` body, validated and snapshotted on the order; no `addresses` table, no `/me/addresses` in v1; billing address not collected (Stripe collects card billing details) | **Gave up:** a saved address book (`/me/addresses` CRUD) | Feature 4 needs an address per order, not an address book. Snapshotting already makes order history immune to later edits; saved addresses add CRUD, authorization and tests with no v1 feature behind them |
| Shipping methods and tax (v1) | **Chose:** flat per-order rates in config `Shipping:Methods` (+ `Shipping:Countries`, `Store:Currency`) served by `GET /shipping-methods`; one flat `Tax:RatePercent` on goods only, committed default 0 as an owner-set placeholder, rounded once per order half away from zero (§7.4); carriers and tracking URL templates in `Shipping:Carriers` | **Gave up:** a seeded `shipping_methods` table and admin UI; weight/zone rates; a tax provider (Stripe Tax, Avalara — a new external service, a stack change) | No v1 feature edits rates, so a table would be schema without a writer. Config keeps the totals server-side and testable (test 23) with zero migrations. The real tax rate is a business decision — never invented by an agent |
| Stripe client SDKs (planned Slice 4 packages) | **Chose:** native `@stripe/stripe-react-native` PaymentSheet (via `npx expo install`, config plugin in `app.json`, works in Expo Go and cloud EAS builds — no local native tooling); web `@stripe/stripe-js` + `@stripe/react-stripe-js` Payment Element. Both behind `lib/platform.native.tsx` / `lib/platform.web.tsx` (rule 17), confirming the server's `client_secret` only; Jest switches to per-platform projects in the same slice (§11.3) | **Gave up:** one SDK everywhere (`stripe-react-native` has no web target; Stripe.js can't run natively); Stripe Checkout / hosted page in a WebView (redirect flow, adds `react-native-webview`, moves away from PaymentIntents) | Matches app context §4.5.4 (Stripe.js on web, RN SDK on mobile) and the stack lock (PaymentIntents, Expo one codebase, cloud EAS). Card data never touches our code; the publishable key is a config placeholder (open decision §2) |
| Retry payment and multiple intents (Slice 4) | **Chose:** retry = new payment attempt + new intent on the same order, `Idempotency-Key` required, allowed only while `PendingPayment` and `expires_at` > now, never extends the TTL; the previous intent gets an outbox cancel; a success on a second intent of an already-`Paid` order is auto-refunded once (§8.2 rules 11–12) | **Gave up:** re-confirming the same intent only; extending the reservation on retry | The docs already promise a new intent per retry. Two live intents can both succeed if the cancel loses the race, so the second success needs a defined, tested outcome (test 25). Extending the TTL would let one customer hold stock indefinitely |
| Admin refund ceiling and idempotency (Slice 6) | **Chose:** lock the paying payment row, check Σ(Pending + Succeeded refunds) + amount ≤ captured in the same transaction that inserts the `Pending` refund, audit row and outbox `RefundRequested`; Stripe key `re:{refundId}`; webhook confirms; partial leaves the order status, full follows §7.3; `process`/`ship` blocked while a full refund is pending (§8.5) | **Gave up:** calling Stripe synchronously in the request; an order-level `PartiallyRefunded` status | Rule 6 forbids the external call in the transaction; the row lock is what stops two concurrent refunds both passing the ceiling. §7.3 has no partial order status and adding one would change the state machine for no v1 screen |
| Local Docker stack (owner request, dev only) | **Chose:** `compose.yaml` adds `api` (root Dockerfile, `Development`, loopback `127.0.0.1:5081`) and `web` (`frontend/apps/store/Dockerfile`: `expo export --platform web` → `nginx:1.27-alpine` with SPA fallback, loopback `127.0.0.1:8082`, API URL as a build arg) next to the unchanged `postgres`; secrets and bootstrap values only from an untracked root `.env`; no startup migration (`database update` stays a separate step, §10.5) | **Gave up:** runtime-configurable web image; a migrator container; any server or cloud deploy | Lets Nathaniel run the whole app in containers without touching his :5080/:8081 debug setup. Production web delivery stays `expo export` → CDN (§2); deploy stays Slice 7 (`slice-plans/local-docker-plan.md`) |
| C# explicit types, no `var` (owner request) | **Chose:** root `.editorconfig` (`csharp_style_var_*` = false, IDE0008 = error) + `EnforceCodeStyleInBuild` in `Directory.Build.props`, so `dotnet build` (local, `verify.sh`, CI) fails on `var`. Exempt by the analyzer itself: anonymous types (and LINQ built on them) and pattern variables | **Gave up:** `var` brevity; the "style never gates" default (§11.4) for this one rule | Owner preference for explicit types in review. Enforced by the compiler instead of review comments, so it costs reviewers nothing and never drifts |
