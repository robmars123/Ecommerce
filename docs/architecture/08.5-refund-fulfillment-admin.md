### 8.5 Cancellation and refund

- Refunds go through `IPaymentGateway` with an idempotency key per refund; webhook-confirmed; the order goes to `Refunded` (or `Returned` for a return) with an audit entry.
- A refund never deletes an order or rewrites totals. It adds a refund record and a status change.
- **Admin refund** (`POST /admin/orders/{id}/refund`, Admin, `Idempotency-Key` scope `refund`, body `{ amount, reason }`):
  1. **Ceiling.** One short transaction locks the order's paying payment row — the attempt that made it `Paid`, status `Succeeded`/`PartiallyRefunded` — (`FOR UPDATE`) and checks `amount > 0` and `Σ(Pending + Succeeded refunds) + amount ≤ payment.amount`. Over the ceiling → 409, no refund row, but the attempt is audited. The lock serialises concurrent refunds, so two requests can never both pass the check.
  2. **Allowed states.** A partial refund: order `Paid`, `Processing`, `Shipped`, or `Delivered`. A refund that reaches the captured amount: only where §7.3 has a transition — `Paid`/`Processing → Refunded`, or `Delivered → Returned` with an `Approved` return request. Otherwise 409. While a full refund is `Pending`, `process` and `ship` on that order → 409, so the webhook's transition is still legal when it lands.
  3. **Same transaction:** insert the refund (`Pending`, its idempotency key), the `audit_log` row (actor, before/after refunded total and payment status, reason), and an outbox `RefundRequested`. Respond 202 with the refund. A repeated key returns the same refund and response; the same key with a different body → 409.
  4. **Stripe after commit:** the `RefundRequested` consumer calls `IPaymentGateway` with Stripe idempotency key `re:{refundId}`, so a consumer retry never makes a second Stripe refund.
  5. **Webhook-confirmed** (`charge.refunded` / `refund.updated`, deduped by event ID): one transaction sets the refund `Succeeded` (or `Failed`, which frees its amount under the ceiling and alerts), moves the payment to `PartiallyRefunded` or `Refunded`, applies the full-refund order transition with a history row, and writes the outbox event. Order totals never change.
- Automatic refunds (§8.2 rules 8 and 12, saga §8.8.4) use the same path and ceiling with `actor_id` null.
- **No auto-restock in v1.** Restock is a separate, audited admin stock adjust with a reason.

### 8.6 Fulfillment

Manual in v1: `Paid → Processing` (admin picks) → `Shipped` (carrier + tracking; `OrderShipped` → email) → `Delivered`. Automation can plug into the same transitions later. Compensation on unfulfillable orders: §8.8.4.

- `ship` takes `{ carrierCode, trackingNumber }` (carrier from `Shipping:Carriers`, §7.4; tracking number 1–64 chars) and inserts a `shipments` row in the same transaction as the transition; `deliver` sets `delivered_at`. Every transition (customer, admin, webhook, worker) writes one `order_status_history` row — that table **is** the customer's timeline.

### 8.7 Admin catalog and inventory

- Products are created with `is_active = false`. Images go to object storage; only keys are stored.
- Initial stock is set via an audited adjust, then the product is published.
- An adjust that would make available < 0 is rejected **and audited**.
- Price changes never touch existing orders (snapshots).
- Production data changes happen only through audited endpoints — no direct SQL.
