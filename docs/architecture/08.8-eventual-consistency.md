### 8.8 Eventual consistency (Slice 6b)

#### 8.8.1 The boundary

| Strongly consistent — one Postgres transaction | Eventually consistent — outbox → consumer |
|---|---|
| Checkout + reservation · Paid transition + inventory commit + outbox insert · refunds · stock adjusts · status changes | Dashboard KPIs · search read model · email · SignalR · customer analytics |

Nothing on the left may read from anything on the right. No RabbitMQ, Kafka, or other broker in v1 — the outbox table is the log.

#### 8.8.2 Projectors

- An event carries `event_id`, `aggregate_id`, and a per-aggregate monotonic `aggregate_version`.
- A projector updates its read model **and** inserts `processed_events` in one transaction — so a duplicate delivery is a no-op.
- **Out of order:** the read model stores the last applied version per aggregate. version ≤ stored → skip. version > stored + 1 → gap: retry with backoff, then dead-letter and alert. Never apply past a gap.
- **Sequence gaps:** identity values can commit out of order. Consumers read only up to rows older than a safety window (config, e.g. 2s), or rescan a trailing window; dedupe makes rescans safe.
- **Replay:** truncate the read model, reset the checkpoint to 0, and re-consume. Outbox rows are retained in v1 to make this possible.

#### 8.8.3 Lag and health

- v1 targets (confirmed, Slice 6b plan D6): dashboard and search ≤ 60s behind (`Projections:LagTargetSeconds`), email ≤ 2 min p95. Lag = age of the oldest unprocessed event a projector consumes; **as-of** = that event's `occurred_at`, else now.
- The dashboard shows an **as-of** time. Each projector exposes last processed event, lag, and dead-letter count. Lag beyond target or any dead letter is an alert.
- Orders and payments are always correct even when a projector is stopped.

#### 8.8.4 Fulfillment compensation (saga)

The fulfillment process is a persisted saga keyed by order. If a fulfillment step fails finally (retries exhausted, or admin marks the order unfulfillable with a reason), compensation issues **exactly one** refund (idempotency key = saga ID + step), moves the order to `Refunded`, and audits it. A saga retry never creates a second shipment or a second refund. v1 has no automated fulfillment step (§8.6 is manual), so the final failure is an admin marking the order unfulfillable (`POST /admin/orders/{id}/unfulfillable`); compensation runs asynchronously from a `FulfillmentFailed` outbox event so the refund keeps the payments → orders lock order, and `ship` is rejected once a saga exists.

#### 8.8.6 Slice 6b design (plan D1–D18)

- **Runtime** (`Persistence/Projections`): per event one tx = `processed_events` mark + version gate + apply. Checkpoints (`consumer_checkpoints`) for projectors only; the checkpoint advances past a row only when it is terminal and older than `Projections:SafetyWindowSeconds` (30). Version gate opt-in per aggregate type, versions in `projection_versions`. Side-effect consumers (§8.4) are unchanged.
- **Read models:** Admin `admin_dashboard_orders` (one row per order) + `admin_dashboard_refunds` (one row per refund with an actor, from `RefundSucceeded`); Catalog `catalog_product_sales_daily` (search projector = sales rank; full-text search stays on `products`). KPIs aggregate at read time.
- **Saga:** `fulfillment_sagas` (one per order), refund key `saga:{sagaId}:Fulfill`, amount fixed when the saga starts.
